# Agent Instructions — Dino Engine

## CRITICAL: File editing rules for this environment (Windows / PowerShell)

The `edit_existing_file` tool is **broken in this environment**: it truncates files at the edit point and silently strips UTF-8 BOMs. Do NOT use it for partial edits. Instead:

1. **Small targeted change** → on-disk string replacement via PowerShell:
   ```powershell
   $c = [IO.File]::ReadAllText($path)
   if (-not $c.Contains("old text")) { throw "pattern not found" }
   $c = $c.Replace("old text", "new text")
   [IO.File]::WriteAllText($path, $c)
   ```
2. **Large change / whole-file rewrite** → delete the file and recreate it with `create_new_file`.
3. **Never issue parallel edits to the same file** — concurrent writes corrupt files (observed: two simultaneous edits truncated a file to 10 lines).
4. **Verify after every write**: check line count (`(Get-Content $path).Count`) and/or build.

## Safety net (always available)

This repo is a git repository. If any file gets mangled:

```powershell
git checkout -- .            # restore all modified files to last commit
git diff --stat              # spot-check: huge deletion counts on lightly-touched files = truncation
dotnet build "Dino Engine.sln" -c Debug --nologo   # truncation always breaks the C# build
```

Commit a checkpoint (`git add -A; git commit -m "checkpoint"`) before any multi-file refactor.

## Project notes

- Solution: `Dino Engine.sln` (projects: `Dino Engine/`, `Dino Defenders/`, `Dino WorldLab/`, `Dino NetLab/`, `Dino Launcher/`, `Dino Release/`, `Dino LaunchLab/`). Build with `dotnet build`.
- Terrain uses **fixed-size chunks** streamed in a ring around the camera (`TerrainChunkSystem` + `TerrainQuadTreeSingleton.Chunks`), NOT an LOD quadtree. Tunables are `WorldScene.ChunkSize` and `ChunkRadius`. The radius bounds how far out the camera may zoom (`ArpgGame.FurthestZoom`): change them together or the view passes the end of the terrain.
- Worlds are generated, never authored. `Dino Engine/World/` is headless (no GL) and deterministic per `WorldRequest`: `WorldGenerator` runs `IWorldStage`s over a `WorldData` (Landform, Erosion, Climate, Biome, Site, Road, Settlement, TerrainBake, Water, Vegetation, Finalize). Content is data in `World/Content/` (archetypes, biomes, sites, structures, nature assets, moods). All placement goes through one `PlacementIndex`, so overlap checks are exact across chunks. All randomness comes from `WorldRandom` forks: draw from a new fork rather than an existing stream, or every world after that point changes. Runtime queries are O(1) map lookups (`Height`, `Walkable`, `Passable`). `Passable` keeps clearance around solids, so a character can stand where it is unset: search outward rather than assume they can't. `WorldScene.Enter` swaps a world in; `TerrainChunkSystem` streams `WorldObjects` sectors and ground cover around the camera; models come from `WorldAssetLibrary`, which keeps them across worlds.
- `Dino WorldLab/` tests worlds with no window: `dotnet "Dino WorldLab/bin/Release/net8.0/Dino WorldLab.dll" check --seed 1 --count 100 [--archetype id]`, also `map`, `sheet`, `plan --site Kind`. `WorldValidator` checks are independent of the generator, and include what the game relies on (`CheckPlayable`): run it after any generation change.
- Terrain materials are a per-world palette (`TerrainSurface.Palette`, at most `MaxMaterials`), splatted per texel on the CPU and read once per pixel in `Terrain.frag`. Grass density, height, dryness and colour are per texel too (`grassTextureArray`, `grassColourTextureArray`).
- Characters: `CharacterMotorComponent` + `CharacterMotorSystem` cut velocity down against `Placement` and `Walkable`, so what looks solid is what is solid. `FollowCameraSystem` tracks the player; `Shaders/FocusCutout.glsl` dithers away what stands between the camera and `context.focusPoint`, in `Model.frag` and `Imposter.frag`.
- The game is in `Dino Defenders/`, and always plays as a client talking to a server: read `NETWORKING.md` before changing anything in it. `Server/` decides everything and must never touch `Engine`, `GameSession` or GL (`GameServer` runs headless, on its own thread; `ServerHost` runs it). `Client/` draws and predicts: `GameClient` holds the connection, `HeroPredictor` the hero, `GhostPresenter` turns ghosts into what's drawn. `Gameplay/` is what both share, `Net/` the protocol and the transports with their libraries, `Progression/` plain rules (items, hero, chronicle, save). `UI/` draws with the engine GUI, reads `GameSession.Current` (what this player has been told, not the truth) and acts through `session.Client`. `EncounterSystem` creates a site's people near any hero and destroys them when all have left, so anything that must last belongs in `SiteState`, never on an entity. Saves keep the `WorldRequest` as given: an archetype drawn from the seed must stay unnamed, or loading makes a different world.
- Networking rules, each with a test: `[Replicated]` on a component and a `NetIdentityComponent` on the entity is all it takes to reach clients. `HeroRules.Step` must depend on nothing but the command, the hero's stats and the fixed world, never on other entities, or prediction breaks. Events (`[NetEvent]`) are for show and can be missed. The engine stays free of network libraries: they go in `Dino Defenders/Net/`, behind `INetTransport`. After any change here run `Dino NetLab`: `dotnet "Dino NetLab/bin/Release/net8.0/Dino NetLab.dll" core` and `game`. When mutation testing by hand, `touch` a restored file: `mv` keeps its old timestamp and MSBuild leaves the mutated DLL in place.
- Testers get builds through `Dino Launcher/`, and `release.cmd` (`Dino Release/`) sends one out: read `LAUNCHER.md` before changing either. The launcher targets .NET Framework 4.8 so that it's one small exe needing nothing installed: no NuGet packages, and it must stay byte-for-byte reproducible, or every release replaces every launcher. `Dino Launcher/Update/` is the logic with no UI. `Feed.cs`, `Manifest.cs` and `SignedFile.cs` are compiled into `Dino Release` too, so they must build on both frameworks. Nothing in the game may depend on the launcher, and the game mustn't write into its own folder, as updates replace it whole. Saves must survive an update, as testers carry them across builds. Two builds refuse each other at the door (`Protocol.Build`). After any change here run `Dino LaunchLab`: `"Dino LaunchLab/bin/Release/net48/Dino LaunchLab.exe" core`, `release` and `live`. A check in `core` that the next run could download its way out of proves nothing: ask `Recover` directly, with no network.
- Client systems register in `ArpgGame.RegisterSystems` and must run before `LocalToWorldTransformRootSystem`, server ones in `GameServer`'s constructor. Override `UpdateFrame` for work that isn't per entity (`UpdateInternal` is internal to the engine; `Step` runs a system from outside it). `TerrainChunkSystem` applies deferred commands mid-frame, so anything reading the render grid must allow for an entity that has just gone. `DirtyEntitiesBuffers` is cleared by `RenderSpatialGridSystem`, its reader, and nowhere else. Don't move entities between archetypes in hot paths; prefer a state field, as `EnemyState.Dead` does.
- Scripted runs of the real game, for checking anything visual: `"Dino Defenders.exe" --seed 303 --archetype isle --site BanditCamp --bot true --shot out.png --frames 700`. `--bot true --sweep true` clears a whole world, `--tour folder` photographs one of each site, `--panel name` opens a panel, `--travel N` steps through a waygate, `--host true`, `--join address:port`, `--netsim latency,jitter,loss` and `--dedicated true` are for networking. Frames count from when the hero is in the world. See `GameOptions`. The bot supplies its own input, so a bot run proves nothing about `LocalInput.Read`: also run without it.
- Grass is fully GPU-driven (after Ghost of Tsushima), with no CPU grass system: settings in `GrassSingleton` (F3 Render window), submitted with the visible chunks by `TerrainChunkRenderSystem`. Per view (camera, and each shadow) `GrassRenderer` runs `Shaders/Grass/Grass_Generate.comp`, which scatters blades on a world-seeded grid, clumps them into Voronoi tufts, thins them with distance, culls them and appends finished Bézier blades to a near (15 vertex) and far (7 vertex) list drawn with `glDrawArraysIndirect` (GL 4.3). The `GrassBlade` layout in `Grass/GrassBlade.glsl` must match `GrassRenderer.BladeStride`; the `GrassData` UBO (binding 7) layout in `Grass/GrassField.glsl` must match `GrassRenderer.UploadSettings`. `Terrain.frag` includes `Grass/GrassField.glsl` to tint the ground under the grass, so grass colour and ground tint change together. Grass draws before terrain so blades early-z-reject the terrain's parallax shading.
- Wind is one engine-wide system: settings/state in `WindSingleton` (advanced by `WindSystem`), GPU side in `WindRenderer` (wind map + vegetation spring sim, `WindData` UBO at binding 6), shader API in `Shaders/Wind.glsl`, CPU API in `Physics/Wind/` (`Wind.Sample`, `Wind.AddBlast`). `WindField.cs` mirrors `Wind.glsl` exactly: change both together. Grass, instanced vegetation and volumetric fog all read it; new consumers should too.
- Water: settings/state in `WaterSingleton` (advanced by `WaterSystem`, after `WindSystem`); still water is entities with `WaterBodyComponent` + `PositionComponent` (+ optional `RotationComponent` yaw); the ocean fills all loaded terrain below `SeaLevel`. GPU side in `Rendering/Renderers/PosGeometry/Water*.cs`: `WaterRenderer.SimulationPass` runs at frame start (shore field + ripple sim), the surface pass runs after `LightPass` (forward, over a copy of the lit scene) and blits its depth back into the G-buffer. Shaders in `Shaders/Water/`; `WaterShape.glsl` mirrors `Physics/Water/WaterShape.cs` and the swell set / constants in `Water_Ocean.frag` mirror `WaterWaves.cs`: change both together. Water decides where it stands from the terrain mesh (`WaterShoreField.HeightTexture`), never the parallax-mapped depth buffer. CPU API: `Physics/Water/` (`Water.Sample`, `Water.AddSplash`, `WaterQuery`, `WaterBasins.Find` for placing ponds in terrain hollows). Light systems submit lights to `_waterRenderer` as they do to the fog, which takes only those with `LightsFog`.
- Anti-aliasing is deferred MSAA with no temporal accumulation: settings in `RenderEngine.AntiAliasing` (`AntiAliasingSettings`, F3 Render window), buffers and resolves in `Rendering/Renderers/AntiAliasing/MsaaRenderer.cs`, shader side in `Shaders/AntiAliasing/` (`Msaa.glsl`: `MsaaData` UBO at binding 8, layout must match `MsaaRenderer.UploadUniforms`). Geometry renders into `Msaa.GeometryBuffer` (multisampled; never bind `GBuffer` for geometry). `RenderEngine.GBuffer` is the single-sample G-buffer resolved from it each frame (each pixel's farthest sample, plus an edge-flag attachment 3) for screen-space passes (SSAO, SSR march, water, fog march, bloom, DOF). Everything from lighting to the fog composite renders into `Msaa.SceneBuffer` (shares the geometry depth-stencil), then `ResolveScene` (tone-mapped-weighted) writes the dual buffer for post-processing. A full-screen pass that modifies the scene before the resolve must read the G-buffer per sample: build its shader twice (plain and with the `PER_SAMPLE` define via `new ShaderProgram(vert, frag, new[] { "PER_SAMPLE" })`), use `msaaShadingSample()`/`msaaShadingCoord()`, and draw with `Msaa.DrawSplit` (stencil bit 1 = edge pixels); express read-modify-write as blending. Shaders that write `gl_SampleMask` must pass it through `msaaCoverage()` (ANDs `gl_SampleMaskIn`; AMD otherwise replaces the triangle's coverage and edges lose their anti-aliasing). Alpha-tested materials use `alphaTestCoverage()`; grass widens sub-pixel blades to `GrassRenderer.MinPixelWidth` and covers a matching share of samples (`grassBladeVertex` coverage, `Grass.frag`).
- Lighting: settings in `RenderEngine.Lighting` (`LightingSettings`, F3 Render window, `--render sun=0,bloom=0` on a scripted run), whose switches take one source of light out at a time. Colours are radiance. `LightPass` adds up `AmbientLightRenderer` (`Ambient_Light.frag`: the hemisphere of sky above and ground below, and emission), then the sun, then point lights and spotlights. `SkySYstem` works out the ambient from the entity with `SkyTag` and the sun; the sky is not a light entity, and with sun and sky off and lights and emission out the frame must be black, which is the test for anything new that gives off light. Particles that aren't glowing set `ParticleRenderTag.Lit`, or smoke shines in the dark. Shared surface maths is in `Shaders/Lighting/lightingCalc.glsl`. A local light is an intensity (`ColorComponent`: what it gives at one metre) and a `LightRangeComponent` radius, at which `lightFalloff` reaches exactly zero; fog and water use the same function. Whatever glows should also shine: generators add `AssetLight`s as they do chimneys, and `TerrainChunkSystem` streams them with their objects, so nothing needs placing by hand. Point lights are culled by their renderer and cheap; a shadow map isn't, so `PointLightShadowSystem` lends a few cube maps to the lights nearest the hero, fading them, and leaves terrain and grass out of them (`LocalShadowCasters`, which also skips what a light sits inside). Emission goes through the G-buffer as `encodeEmission`/`decodeEmission`: a vertex colour brighter than 1 on an emissive material keeps its hue in the albedo and its strength in the emission channel, so keep a glow's colour saturated or tone mapping bleaches it. Bloom spreads only light over `BloomThreshold`, kept above sunlit surfaces; lowering that or lengthening the chain lays a veil over the whole picture. Tone mapping is one ACES fit after `Exposure`, in `HDR_Mapper.frag`.
- GUI lives in `Dino Engine/GUI/` (retained-mode element tree, not ECS). `Engine.Gui` is the `GuiContext`; it updates before game/world update and renders to the back buffer at the end of `RenderEngine.Render`. Gameplay input must check `Engine.Gui.WantsMouse` / `WantsKeyboard`. Text uses a built-in TrueType parser/rasterizer reading OS fonts (`GUI/Text/`), no font assets. Shaders: `Shaders/GUI.vert/.frag` (uniform lines must be `uniform type name;` at column 0 for `ShaderProgram`'s parser). Debug overlay (F3): `GUI/Debug/`.
