# Agent Instructions — Dino Engine

## CRITICAL: File editing rules for this environment (Windows / PowerShell)

The `edit_existing_file` tool is **broken in this environment**: it truncates files at the edit point and silently strips UTF-8 BOMs. Do NOT use it for partial edits. Instead:

1. **Small targeted change** → on-disk string replacement via PowerShell:
   ```powershell
   $c = [IO.File]::ReadAllText($path)
   if (-not $c.Contains("old text")) { throw "pattern not found" }
   $c = $c.Replace("old text", "new text")
   [IO.File]::WriteAllText($path, $c)
   ```
2. **Large change / whole-file rewrite** → delete the file and recreate it with `create_new_file`.
3. **Never issue parallel edits to the same file** — concurrent writes corrupt files (observed: two simultaneous edits truncated a file to 10 lines).
4. **Verify after every write**: check line count (`(Get-Content $path).Count`) and/or build.

## Safety net (always available)

This repo is a git repository. If any file gets mangled:

```powershell
git checkout -- .            # restore all modified files to last commit
git diff --stat              # spot-check: huge deletion counts on lightly-touched files = truncation
dotnet build "Dino Engine.sln" -c Debug --nologo   # truncation always breaks the C# build
```

Commit a checkpoint (`git add -A; git commit -m "checkpoint"`) before any multi-file refactor.

## Project notes

- Solution: `Dino Engine.sln` (projects: `Dino Engine/`, `Dino Defenders/`, `Dino WorldLab/`, `Dino NetLab/`, `Dino BuildLab/`, `Dino GearLab/`, `Dino AnimLab/`, `Dino SoundLab/`, `Dino Launcher/`, `Dino Release/`, `Dino LaunchLab/`). Build with `dotnet build`.
- Terrain uses **fixed-size chunks** streamed in a ring around the camera (`TerrainChunkSystem` + `TerrainQuadTreeSingleton.Chunks`), NOT an LOD quadtree. Tunables are `WorldScene.ChunkSize` and `ChunkRadius`. The radius bounds how far out the camera may zoom (`ArpgGame.FurthestZoom`): change them together or the view passes the end of the terrain.
- Worlds are generated, never authored. `Dino Engine/World/` is headless (no GL) and deterministic per `WorldRequest`: `WorldGenerator` runs `IWorldStage`s over a `WorldData` (Landform, Erosion, Climate, Biome, Site, Road, Settlement, Camp, TerrainBake, Water, Vegetation, Finalize, Pack). Content is data in `World/Content/` (archetypes, biomes, sites, structures, nature assets, moods). All placement goes through one `PlacementIndex`, so overlap checks are exact across chunks. All randomness comes from `WorldRandom` forks: draw from a new fork rather than an existing stream, or every world after that point changes. Runtime queries are O(1) map lookups (`Height`, `Walkable`, `Passable`). `Passable` keeps clearance around solids, so a character can stand where it is unset: search outward rather than assume they can't. `WorldScene.Enter` swaps a world in; `TerrainChunkSystem` streams `WorldObjects` sectors and ground cover around the camera; models come from `WorldAssetLibrary`, which keeps them across worlds.
- `Dino WorldLab/` tests worlds with no window: `dotnet "Dino WorldLab/bin/Release/net8.0/Dino WorldLab.dll" check --seed 1 --count 100 [--archetype id] [--level N] [--people percent] [--packs percent]`, also `map`, `sheet`, `plan --site Kind`, and `wind`, which puts the wind through what a game does to it. `WorldValidator` checks are independent of the generator, and include what the game relies on (`CheckPlayable`): run it after any generation change.
- Terrain materials are a per-world palette (`TerrainSurface.Palette`, at most `MaxMaterials`), splatted per texel on the CPU and read once per pixel in `Terrain.frag`. Grass density, height, dryness and colour are per texel too (`grassTextureArray`, `grassColourTextureArray`).
- Characters: `CharacterMotorComponent` + `CharacterMotorSystem` cut velocity down against `Placement` and `Walkable`, so what looks solid is what is solid. `FollowCameraSystem` tracks the player; `Shaders/FocusCutout.glsl` dithers away what stands between the camera and `context.focusPoint`, in `Model.frag` and `Imposter.frag`.
- The game is in `Dino Defenders/`, and always plays as a client talking to a server: read `NETWORKING.md` before changing anything in it. `Server/` decides everything and must never touch `Engine`, `GameSession` or GL (`GameServer` runs headless, on its own thread; `ServerHost` runs it). `Client/` draws and predicts: `GameClient` holds the connection, `HeroPredictor` the hero, `GhostPresenter` turns ghosts into what's drawn. `Gameplay/` is what both share, `Net/` the protocol and the transports with their libraries, `Progression/` plain rules (items, hero, chronicle, save). `UI/` draws with the engine GUI, reads `GameSession.Current` (what this player has been told, not the truth) and acts through `session.Client`. `EncounterSystem` creates a site's people near any hero and destroys them when all have left, so anything that must last belongs in `SiteState`, never on an entity. Saves keep the `WorldRequest` as given: an archetype drawn from the seed must stay unnamed, or loading makes a different world.
- A fight is books: read `BOOKS.md` before changing anything an actor can do. There are no skills: everything a hero or an enemy does, from a sword swing to a meteor, is a book of sentences. A hero's is an item, on `HeroState.Bar` (six slots: LMB, RMB, Q, 1, 2, 3), and an enemy's is on `Shelf`. Books, pages and stickers are all items that are found, and each holds the next (`Item.Held`), with better ones having more places: `Scribe.Bind` makes a `Book` of them, an `ItemPlace` can be inside something (`In`), and everything moves by `HeroState.Move`. A book is Active, Trigger or Toggle (`Item.Mode`): a Trigger Book's conditions only count in a blow (`Combat.Watch`) and it goes off in `GameServer.GoOff`, and a Toggle Book holds only Area Pages, goes on and off in `HeroRules.Step` and takes its Cost off Mana Regeneration there, so both stay predicted. A sticker is one good thing and one bad thing, rolled by `Stickers.Roll`. A page's Potency goes on to the next, by what's on the page and not what a build adds. An Area Page is always last, and a page can't change kind. `Books/` has no GL and no server in it. `Scribe.Fix` makes sense of whatever a save or a stranger sends, `Scribe.Read` makes a `BookPlan` of the sentences, and `ActorSheet.Profile` makes that a `BookProfile` with a `PageProfile` for each page, which is all a blow reads. A sentence is a line in `Sentences`, and its `Weights` are each a multiplier of their own, so nothing stacks to zero. Your Damage is the weapon's for every book and a wand or staff makes it a Spell, so wand and staff bases are what a caster lives on. Pages turn through `Combat.Turn` on the deferred list, carrying a `Cast`, and `Spend` stops a cast at `MostMade`, as no balance number can stop a book branching. A page that turns on someone goes through them (`off`), and a leap keeps count of `Chains`. `PageSign` is all a client knows of a page. An enemy's first page starts from them or where they aim, or a mark would promise something that hasn't been chosen. After any change here run `Dino BuildLab check`, `Dino NetLab books` and `Dino NetLab build`, and `Dino BuildLab books` for what each sentence comes to. Nobody has played this: those numbers are only where to start.
- Stats, books, the talent tree, items and enemies are one system: read `BUILDS.md` before changing any of them. A hero, an enemy and a minion are all an `Actor` (`Server/Actor.cs`) with a `Loadout` of `Mod`s, compiled to an `ActorSheet`, and `Combat` doesn't know which it has: never give one of them a rule of its own. The per-blow path is `Stats/Hits.cs`, which reads finished numbers and must not allocate: `bench` fails if it does. Whatever a blow sets off goes on `Combat`'s deferred list and happens on the next pass, as an explosion that kills something that explodes would otherwise recurse through a list being iterated. `Stats/` has no GL and no server in it. Both ends of a connection compile the same sheet from the same `HeroState`, so everything is gathered in a fixed order: `Loadout` keeps equal stats in the order they came, and `HeroBuild` walks slots and sorted talents. Stats, rules, sentences and uniques that nothing uses or that change nothing fail `check`. Item lines are an affix id and a value, so affix ids, unique ids and the order of a sector's pods in `TalentContent` are saved data: names and numbers can change freely, those can't. After any change here run `dotnet "Dino BuildLab/bin/Release/net8.0/Dino BuildLab.dll" check` and `dotnet "Dino NetLab/bin/Release/net8.0/Dino NetLab.dll" build`. `Bestiary.HealthAt` and `DamageAt` are fitted to the table `balance` prints, not to any person's opinion: nobody has played this yet.
- Tooltips are the ground truth: read `TOOLTIPS.md` before changing any, or adding a stat, rule, tag, condition or sentence. Nothing a player reads is written by hand. Every number in the rules that isn't on a stat is in `Stats/Rulebook.cs`, never a literal in the code that uses it, and `Combat` and the text both read it. `Tooltips/` is headless: `ModText` turns a `Mod` into a sentence by fixed rules (`+5` flat, `increased` a shared sum, `more` a multiplier of its own), `Lexicon` is every word that means something, `StatBook` the hero's sheet, and `Cards` builds a `Card` from finished numbers. A card is built again each frame it's shown, so it's live, and `UI/Tips.cs` (`GameUi.Current.Tips.Show`) is the only thing that draws one. A person called the first version unreadable, so nothing opens by itself and nothing sticks: a card stays short, and holding left Ctrl holds it still so that a marked word or tag can open that word alone, and `Details` the rest. Definitions stay short and plain, in the words any ARPG would use. A stat's card shows total flat, total increased and each more on its own. A naked hero has 100 Life, 100 Mana and nothing else at any level, which `check` holds: what can't be zero is a rule with the sheet showing the bonus on top, and power comes from attributes on the tree (read What a hero starts with in `BUILDS.md`). A capitalised word is a defined term, always: `check` reads every sentence the game can show and fails on a capitalised word that isn't a term, a term in lower case, a digit typed into a string, a number in a fight that isn't in the `Rulebook`, and a stat, rule, condition or tag with no words. When something reads wrong the fix is rarely in the text: either the number's in the wrong place or the rules don't do what it says, so fix that. After any change here run `Dino BuildLab check` and `Dino NetLab build`, read `list --what cards`, and judge a card in the real game with real mouse messages.
- Animation is made, never stored: read `ANIMATION.md` before changing it. The rules own time and bodies follow: nothing in the rules waits for, reads or is moved by an animation, and a pose is worked out each frame from where a body is and what it's been told (`AnimationInput`), so a swing can be cut off at any moment with nothing else having to know. `Dino Engine/Animation/` is headless. `Gait` is the only thing that moves a foot, which stays exactly where it is until it lifts. A `Gesture` is three keys, and `GesturePlayer.Sample` is a pure function of how long it's been, so Contact is on the tick the rules say. `SkillMotions.Of` picks one from a page's `PageSign`, so a new book looks right with nothing added. What isn't a book goes by `FlourishEvent`. `Ragdoll` is Verlet points and can't blow up, and `IGround.LookAround` is asked once a step, not once a point, as most ground has nothing on it. Solids have heights in `PlacementIndex` only for what flies. Model space is +Z forward, +Y up and +X to the body's left. `CharacterAnimator` must not allocate: `bench` says so. After any change here run `Dino AnimLab check` and `Dino NetLab combat`. Judge how anything moves from `sheet` and the real game, as `check` can only say nothing went wrong.
- A fight shows what's coming, and that's a promise: read the second half of `ANIMATION.md` before changing combat. `GroundShape` is the one description of what an attack covers: the server tests against it and a client draws it, so nothing may find who's in an area but `Combat.Within`. `Grid.Foes` adds a body's whole width, which isn't what's marked. When the fill reaches the edge it lands, on that tick: a wind-up is `WindUpTicks`, in ticks that really pass, fixed when it starts, and whatever stops it withdraws its mark. `Time` is ticks and goes on while someone alone has stopped the world, so what's waiting moves along with it (`TelegraphSystem`, `Combat.Wait`), and a client reads a mark's times each frame. A client knows a mark by its `Serial`, as entity ids go to the next thing made at once. Two colours only. Marks can only be judged moving and by a person, and never from a `--film`, where corrections restart blows and marks pile up in rings. `Dino NetLab combat` has been seen to fail with each of its bugs put back: keep it that way. Nothing about input can be proved by a bot: post real messages and read them with `--trace`.
- Gear is one mesh per item, grown from a seed: read `GEAR.md` before changing how anything worn, held or dropped looks. Nothing about a look is saved or sent but `Item.LookSeed` and `ItemLook.Traits`, and what's in the hand, on the ground and in the icon are all that one mesh, so never give any of them a model of its own: the only other is a book being read, which is that book laid open (`GearKind.OpenBook`). `Dino Engine/Modelling/Procedural/Gear/` is headless and knows nothing of the game: `GearForge.Make` takes a `GearSpec`. It runs on worker threads, so it can't touch anything shared, and it can't read `TextureGenerator`, as any static on that class compiles shaders: materials come through `GearMaterials`. Every number in a look comes from `Genes`, by a name of its own, so a new parameter moves nothing else. A shape is never picked from a list: `ItemLook.Forms` is ranges to start from, and is the only hand-written data. Families are shares worked out from an item's base numbers, never stored, and a part belongs to one by `ArmourCut.Likely`. Armour is offset from `BodyForm`, which has to agree with `HumanoidGenerator`, and what's under it is left out of the body (`BodyRegions`). `ItemSlot` is what an item is worn as and `WornSlot` is one of the ten places on a hero, so a ring is one of the first and either of two of the second. Anything using a model from `GearWorkshop` has to keep asking for it every frame, which is what keeps it alive. `ItemStudio` draws pictures and the hero on the character screen, and its output is premultiplied. After any change here run `Dino GearLab check`, `variety --heavy 1`, `--leather 1` and `--cloth 1`, `Dino BuildLab check` and `Dino NetLab gear`. Judge looks from `sheet`, `dress` and the real game (`--wear heavy --panel hero`). To post real mouse messages to a hidden run, post `WM_SETFOCUS` first, as the interface ignores the mouse unless it has the focus.
- Loot is one system: read the Loot section of `BUILDS.md` before changing it. `Progression/Loot.cs` is the rules and has no GL and no server in it: `LootTables` is one row per `LootTier`, `TierOf` reads a tier from an enemy's real health, `LootLuck` shortens dry spells, and `GradeOf` is worked out from the item and never stored. A masterwork is a rare with `MasterworkLines` lines, so nothing else may roll that many. `Server/GroundLoot.cs` owns what's on the ground, and nothing may reach a pack but by `Ask` and `Serve`: no auto pickup, ever, for anything but gold. `PickupComponent` carries everything a drop needs to be shown, so never move any of that to an event. Item names can't go in it, so they come by `Message.GroundItem`. `Client/LootShow.cs` shows a drop and `LootFetch` walks the hero to a click, and `UI/LootLabels.cs` is the labels. `Treasure.LegendaryStrike` is a legendary's flight time and the moment its sound breaks: they're one number. Beams are `BeamComponent` (`BeamRenderer`, `Shaders/Beam.frag`), which also covers a little of what's behind them, as light that's only added goes white over a sunlit field. After any change here run `Dino BuildLab check`, `Dino NetLab loot`, and `Dino NetLab pace` for how often something good comes. Nothing about clicking can be proved by a bot: post real mouse messages, including a held attack dragged across a label, which must take nothing and stay an attack. Boxes that push each other up go through `LabelStack.Lift`, for labels and marks alike: a loop that starts over when one moves must only do so if it really went up, as near the top of the screen float rounding left a lifted box still touching, and the game froze there for good.
- What's carried stays where it was put: read The pack in `GEAR.md` before changing it. `HeroState.Inventory` is fixed cells with gaps in them, never a list, and only `HeroState.Sort` moves anything by itself, when asked. Selling leaves a gap and whatever comes off goes into the cell it came from. All the rules are on `HeroState` and `MerchantTable`, as both ends run them: a client changes what's carried at once (`GameClient.AskGear`) and the server has the last word, answering each change with the truth (`ServerPlayer.Heard`), so anything that changes a pack has to go through those two: read the NETWORKING.md part on it. Anything on `HeroState` that isn't data has to be a method, or it's saved. What's on the cursor is `HeroPanel._hand`, which only says where the item really is, and all a click can do is in `PlanFor`, which is also what the caption says, so never give the two separate logic. Ctrl is shared with holding a card still, which is what `loose` on `TipLayer.Show` sorts out. After any change here run `Dino BuildLab check` and `Dino NetLab pack`, and for anything about clicking, real mouse messages: read modifiers from `Context.Modifiers`, as posted keys never reach the mouse event's.
- Offerings are what gold is for: read the Offerings section of `BUILDS.md` before changing them. `Progression/Offering.cs` is the rules: peril (the key level), `Teeming` and `Overrun` (more enemies, none stronger, paying nothing more each) and `Omens` (a saved id each, sent by their order, so a new one goes on the end). It's chosen at a waygate for a new land, and `GameServer.Pay` is what charges for it. More enemies are part of the world: `Offering.Shape` makes a `WorldRequest` with `MorePeople` and `MorePacks`, which only `PackStage` reads, and that has to stay so, or a save or a friend grows a different land. Anything that reads what something is worth from its health has to divide `Offering.EnemyHealth` back out. `LootBoon.None` must leave a roll as it was. `Falls`, `Broken` and `HeroState.PerilProven` are the rest of what's kept. A buff rebuilds an enemy's loadout in `ServerSession.Rebuild`, which must keep its rules and triggers. After any change here run `Dino BuildLab check`, `Dino NetLab offering` and `Dino WorldLab check --people 150 --packs 100`, and `Dino BuildLab offering` for how the climb pays.
- Packs are what most of a world's fighting is: read the Packs section of `BUILDS.md` before changing them. `CampStage` and `PackStage` decide where and whose (`WorldData.Haunts`, each a `WorldSite` of `SiteKind.Haunt` that the game keeps as a `Wild` `SiteState`), `Territory` says whose ground it is, and `Warbands` in the game says who's in them. Add to a site's `Spawns` only at the end, as the dead are kept by number. `EnemyBrainSystem.CallReach` has to stay below `PackStage.Spacing`, or one fight wakes the next. `Bestiary.Everyone` must list every kind, and a new `Look` needs a line in `CharacterFactory.Resolve`, or it's drawn as a villager, and in `BearingOf`, which says how it moves and what it holds. Animals are on the same bones as people with their joints elsewhere (`BeastGenerator.RigOf`), and the arms are the forelegs. After any change here run `Dino WorldLab check`, whose `CheckPacks` holds the density a player feels, `Dino BuildLab density` for the numbers, and `Dino NetLab pace` for how it plays: a real client on foot from pack to pack.
- What can be used is marked: `UI/UseMarks.cs` draws one for every `InteractableComponent`, so a new kind needs only its lines in `NameOf`, `ColourOf`, `HeightOf` and `DrawIcon`. One shape, a dark pill with a stem, means "this can be used", and it's the only place the use key is shown: in reach it grows to name the key and the action, on `session.OfferedThing`, which `PromptSystem` picks by the same rule as the server. Clicking one walks the hero there and presses use (`LootFetch.BeginUse`), which waits until the thing is `UseMargin` inside its reach and nearer than anything else by as much, as the server gives a press to whatever's nearest where it has the hero. Only marks themselves stop the mouse, on the same terms as a find's label, and the world model under one doesn't take a click, as enemies stand around these things. Marks keep clear of what loot and enemies mean: don't use a mark's shape or a beam for anything else. A shrine or gate is used from a few metres in front of its model, and the mark looks the model up (`WorldObjects.TryNearest`). Anything that can be used has to be there to see: `SiteBuilder.Place` fails silently, so what a site can't do without goes through `PlaceNear`, and `WorldValidator` fails an altar or waygate spawn with nothing standing on it. An altar stands in the middle of its site, so anything sending a hero to a site's position goes by `TryFindGround`, and a road that ends there stops short of it as it does at a church. A person who can be used speaks from over their mark (`SpeechOverMark`). Marks can't be judged by a bot: post a real `E`, a real click on one, and a held attack dragged across one, which must stay an attack and walk nowhere.
- Networking rules, each with a test: `[Replicated]` on a component and a `NetIdentityComponent` on the entity is all it takes to reach clients. `HeroRules.Step` must depend on nothing but the command, the hero's stats and the fixed world, never on other entities, or prediction breaks. Events (`[NetEvent]`) are for show and can be missed. The engine stays free of network libraries: they go in `Dino Defenders/Net/`, behind `INetTransport`. After any change here run `Dino NetLab`: `dotnet "Dino NetLab/bin/Release/net8.0/Dino NetLab.dll" core`, `game`, `build`, `books`, `loot` and `pack`. When mutation testing by hand, `touch` a restored file: `mv` keeps its old timestamp and MSBuild leaves the mutated DLL in place.
- Testers get builds through `Dino Launcher/`, and `release.cmd` (`Dino Release/`) sends one out: read `LAUNCHER.md` before changing either. The launcher targets .NET Framework 4.8 so that it's one small exe needing nothing installed: no NuGet packages, and it must stay byte-for-byte reproducible, or every release replaces every launcher. `Dino Launcher/Update/` is the logic with no UI. `Feed.cs`, `Manifest.cs` and `SignedFile.cs` are compiled into `Dino Release` too, so they must build on both frameworks. Nothing in the game may depend on the launcher, and the game mustn't write into its own folder, as updates replace it whole. Saves must survive an update, as testers carry them across builds. Two builds refuse each other at the door (`Protocol.Build`). Release notes are always a list of changes, written for the people playing, never a paragraph (`Publisher.AsList`). After any change here run `Dino LaunchLab`: `"Dino LaunchLab/bin/Release/net48/Dino LaunchLab.exe" core`, `release` and `live`. A check in `core` that the next run could download its way out of proves nothing: ask `Recover` directly, with no network.
- Client systems register in `ArpgGame.RegisterSystems` and must run before `LocalToWorldTransformRootSystem`, server ones in `GameServer`'s constructor. Override `UpdateFrame` for work that isn't per entity (`UpdateInternal` is internal to the engine; `Step` runs a system from outside it). `TerrainChunkSystem` applies deferred commands mid-frame, so anything reading the render grid must allow for an entity that has just gone. `DirtyEntitiesBuffers` is cleared by `RenderSpatialGridSystem`, its reader, and nowhere else. Don't move entities between archetypes in hot paths; prefer a state field, as `EnemyState.Dead` does.
- Hangs leave a trail: `HangWatch` notices when the main loop has stopped for 30 s, logs what each thread is doing, and has a second copy of the game write `hang.dmp` (several GB, the last one replacing the one before) beside `game.log`. Read it with `dotnet-dump analyze hang.dmp`, then `clrthreads`, `setthread 0` and `clrstack -a`. It has to be a full dump: asking for private memory alone, as `dotnet-dump --type Heap` does, fails on this machine with error 1, and `createdump` no longer takes a process id. A hang that needs a long session can be had by running `--bot true --sweep true --hidden true` for 20 minutes on a few seeds.
- Performance has rules. Run `--perf file --size 3440x1369 --hidden true` before and after anything that might cost, at a place with something in it, and read the report: frame times with their percentiles, every pass and task, triangles, and what took the time in slow frames. `--meshseed N` grows the same plants in two builds, so that their pictures can be compared, and `--wind 0:0:0` stills them. `--perfgpu false` turns the pass timers off, which only run while the F3 Performance window is open (`PerformanceMonitor.MeasureGPU`). Nothing the camera or a shadow can't use goes to the GPU: models are culled by a sphere that holds everything the wind can lean them to (`glModel.WorldBounds`), and the sun's casters by the path of their shadow (`Frustum.IntersectsSweptSphere`), as the sun's maps are only read for what's in view. A thing's triangles are paid for thousands of times over: a flower is a few pixels from up here, so a detail smaller than a pixel at the closest zoom is a fault, however good it would look from the ground. A flat card is one quad, and a stem a centimetre thick isn't a 32-sided tube. A blade costs its pixels and not its vertices: the vertex stage is 0.4 ms of a 4 ms field, so fewer segments or attributes buy nothing. Writing `gl_SampleMask` stops depth being tested first, and it's what makes thin things look right, so it stays, but grass is drawn twice for it: `Grass_Depth.frag` settles which blade owns each sample, with no colour, and `Grass.frag` then shades only those, on an equal depth test, which is why `Grass.vert` has to stay `invariant`. Anything that costs a field is best looked for at a place with tall thick grass, a hillside, and not a village: the same pass costs twice as much there, and that's what someone with a slow frame is looking at. The frame rate is limited by `EngineLaunchSettings._frameRateLimit`, which `--maxfps` overrides, and a scripted run keeps to 60, as its `--frames` are how long it lasts. Whatever runs in frames has to mean the same thing at any rate: use the delta, or seconds. Crossing into a chunk used to bring a whole row of them at once and stall the GPU on small uploads, so they come `ChunksPerFrame` at a time.

For real input, post window messages to the game (`WM_KEYDOWN` with the scan code in `lParam`, and always a `WM_MOUSEMOVE` first, as GLFW takes the mouse's position only from moves) in a run with `--shot` and `--frames`, which keeps real time, and read the HUD from the shot. Nothing about timing between client and server can be judged from a `--film`: its client is on a fixed step and saves about 4 frames of world a second while the server keeps real time, so even a held mouse button goes wrong in one. The game's window can't be read from outside (`PrintWindow` and screen copies come back white). "Joined from this machine" prints about 5 s before the world is on screen, and input until then lands on the loading screen, where a mouse press holds `WantsMouse` until it's released.
- Grass is fully GPU-driven (after Ghost of Tsushima), with no CPU grass system: settings in `GrassSingleton` (F3 Render window), submitted with the visible chunks by `TerrainChunkRenderSystem`. Per view (camera, and each shadow) `GrassRenderer` runs `Shaders/Grass/Grass_Generate.comp`, which scatters blades on a world-seeded grid, clumps them into Voronoi tufts, thins them with distance, culls them and appends finished Bézier blades to a near (15 vertex) and far (7 vertex) list drawn with `glDrawArraysIndirect` (GL 4.3). The `GrassBlade` layout in `Grass/GrassBlade.glsl` must match `GrassRenderer.BladeStride`; the `GrassData` UBO (binding 7) layout in `Grass/GrassField.glsl` must match `GrassRenderer.UploadSettings`. `Terrain.frag` includes `Grass/GrassField.glsl` to tint the ground under the grass, so grass colour and ground tint change together. Grass draws before terrain so blades early-z-reject the terrain's parallax shading, in two passes (see the performance rules).
- The game's camera is some 33 m from the hero and 67° up, and grass must be tuned from there, not from the ground: `FalloffStart` and `LodDistance` have to clear that distance or the player only meets the thinned far end of the field. From above a blade shows mostly its upper half, so a field reads by its tips (bleach them and it goes pale), an upright blade is a dot (hence the lean and droop), and what the eye takes in is masses, not blades: `grassSwell` (height), `grassCombAngle` (lean), `grassPainted` (warm light to cool deep) and the field normal, which lights blades as one soft surface. `windCrest` rolls waves down the wind, and gusts brighten what they lean over. `fragCanopy` darkens by depth in the field, relative to the height around a blade, not along the blade. Cover decides where tufts grow, and the ground decides for a whole tuft, so sparse grass stands in colonies of bunches: don't make cover shrink blades again, or thin ground goes back to specks. Blades can be plumes or blooms (`GRASS_PLUME`, `GRASS_BLOOM`), per biome (`GrassPlumes`, `GrassBloom`, its colours), by the bloom map and the colour map's alpha. Grass.frag cuts petals and feathers plumes with the sample mask, needing no discard. Grass colours are albedos under a sun of about 13: anything pale goes white, so keep flowers and seed heads deep and saturated. A low look at a place: `--look 5 --angle 14`.
- Wind is one engine-wide system: settings/state in `WindSingleton` (advanced by `WindSystem`), GPU side in `WindRenderer` (wind map + vegetation spring sim, `WindData` UBO at binding 6), shader API in `Shaders/Wind.glsl`, CPU API in `Physics/Wind/` (`Wind.Sample`, `Wind.AddBlast`). `WindField.cs` mirrors `Wind.glsl` exactly: change both together. Grass, instanced vegetation and volumetric fog all read it; new consumers should too. After any change here run `Dino WorldLab wind`.
- The wind is built like Ghost of Tsushima's, a steady vector with slow noise on it, and a field of plants shows up any fault in it, so it has rules. Whatever moves with the wind keeps a running total in `WindSystem.Advance` and adds to it each step: never multiply a clock by a live speed, or the phase jumps by all the time so far at every change, and waves strobe and run backwards, worse the longer the session. Totals wrap at a whole number of cycles of everything that reads them (`WaveCyclesPeriod`, `FlutterCyclesPeriod`). Never rotate a pattern with the wind: about a far-off world origin it slides at hundreds of metres a second. Waves come from a fixed rose of directions and fade from one to the next (`WindField.WaveTrain`), and noise is carried along by a running offset. Heading and speed ease apart, so a reversal swings round at full strength rather than dying through nothing. Nothing at rest follows the live wind: the field's comb reads `Prevailing`, which stays put, as `wind.Direction` only changes for the guiding wind. What plants read stays broad and slow: curl noise at a few metres is for particles, and quick noise on grass reads as a fault. Patterns travel at `PatternSpeed`, which levels off, so a gale leans the field further rather than making it frantic. Waves go through the spring (`vegetationTargetBend`), so trees and grass move with the same event. The spring stays near critical damping, and stiffness varies in smooth patches: low damping rings at whatever gust frequency matches it, and per-texel stiffness puts neighbours out of step, so the field boils. A blade's pose must be continuous in everything it reads: its droop passes through nothing as the wind stands it up (`droopPull`), its face is a line (`asLine`), and its flutter stays out of both. Flutter is per tuft and under 2 Hz. Judge any of this moving, with `--film`, never from a still.
- Water: settings/state in `WaterSingleton` (advanced by `WaterSystem`, after `WindSystem`); still water is entities with `WaterBodyComponent` + `PositionComponent` (+ optional `RotationComponent` yaw); the ocean fills all loaded terrain below `SeaLevel`. GPU side in `Rendering/Renderers/PosGeometry/Water*.cs`: `WaterRenderer.SimulationPass` runs at frame start (shore field + ripple sim), the surface pass runs after `LightPass` (forward, over a copy of the lit scene) and blits its depth back into the G-buffer. Shaders in `Shaders/Water/`; `WaterShape.glsl` mirrors `Physics/Water/WaterShape.cs` and the swell set / constants in `Water_Ocean.frag` mirror `WaterWaves.cs`: change both together. Water decides where it stands from the terrain mesh (`WaterShoreField.HeightTexture`), never the parallax-mapped depth buffer. CPU API: `Physics/Water/` (`Water.Sample`, `Water.AddSplash`, `WaterQuery`, `WaterBasins.Find` for placing ponds in terrain hollows). Light systems submit lights to `_waterRenderer` as they do to the fog, which takes only those with `LightsFog`.
- Anti-aliasing is deferred MSAA with no temporal accumulation: settings in `RenderEngine.AntiAliasing` (`AntiAliasingSettings`, F3 Render window), buffers and resolves in `Rendering/Renderers/AntiAliasing/MsaaRenderer.cs`, shader side in `Shaders/AntiAliasing/` (`Msaa.glsl`: `MsaaData` UBO at binding 8, layout must match `MsaaRenderer.UploadUniforms`). Geometry renders into `Msaa.GeometryBuffer` (multisampled; never bind `GBuffer` for geometry). `RenderEngine.GBuffer` is the single-sample G-buffer resolved from it each frame (plus an edge-flag attachment 3), for the light passes' per-pixel variants and the screen-space passes (SSAO, SSR march, water, fog march, bloom, DOF). A pixel's samples that lie on much the same plane are averaged there and lit once, as light is linear in what it falls on: only samples on different things, by normal, depth or emission, make an edge pixel, which is lit per sample and holds its farthest sample here. Grass makes nearly every pixel a mix of surfaces, so don't go back to calling any difference in colour an edge: that's what once shaded a whole field four times over. Everything from lighting to the fog composite renders into `Msaa.SceneBuffer` (shares the geometry depth-stencil), then `ResolveScene` (tone-mapped-weighted) writes the dual buffer for post-processing. A full-screen pass that modifies the scene before the resolve must read the G-buffer per sample: build its shader twice (plain and with the `PER_SAMPLE` define via `new ShaderProgram(vert, frag, new[] { "PER_SAMPLE" })`), use `msaaShadingSample()`/`msaaShadingCoord()`, and draw with `Msaa.DrawSplit` (stencil bit 1 = edge pixels); express read-modify-write as blending. Shaders that write `gl_SampleMask` must pass it through `msaaCoverage()` (ANDs `gl_SampleMaskIn`; AMD otherwise replaces the triangle's coverage and edges lose their anti-aliasing). Alpha-tested materials use `alphaTestCoverage()`; grass widens sub-pixel blades to `GrassRenderer.MinPixelWidth` and covers a matching share of samples (`grassBladeVertex` coverage, `Grass.frag`).
- Lighting: settings in `RenderEngine.Lighting` (`LightingSettings`, F3 Render window, `--render sun=0,bloom=0` on a scripted run), whose switches take one source of light out at a time. Colours are radiance. `LightPass` adds up `AmbientLightRenderer` (`Ambient_Light.frag`: the hemisphere of sky above and ground below, emission and the sun, which it takes from `DirectionalLightRenderer.TakeSun` so that the scene is written once and not read back), then whatever directional light has no cascades (lightning), then point lights and spotlights. `SkySYstem` works out the ambient from the entity with `SkyTag` and the sun; the sky is not a light entity, and with sun and sky off and lights and emission out the frame must be black, which is the test for anything new that gives off light. Particles that aren't glowing set `ParticleRenderTag.Lit`, or smoke shines in the dark. Shared surface maths is in `Shaders/Lighting/lightingCalc.glsl`. A local light is an intensity (`ColorComponent`: what it gives at one metre) and a `LightRangeComponent` radius, at which `lightFalloff` reaches exactly zero; fog and water use the same function. Whatever glows should also shine: generators add `AssetLight`s as they do chimneys, and `TerrainChunkSystem` streams them with their objects, so nothing needs placing by hand. Point lights are culled by their renderer and cheap; a shadow map isn't, so `PointLightShadowSystem` lends a few cube maps to the lights nearest the hero, fading them, and leaves terrain and grass out of them (`LocalShadowCasters`, which also skips what a light sits inside). Emission goes through the G-buffer as `encodeEmission`/`decodeEmission`: a vertex colour brighter than 1 on an emissive material keeps its hue in the albedo and its strength in the emission channel, so keep a glow's colour saturated or tone mapping bleaches it. Bloom spreads only light over `BloomThreshold`, kept above sunlit surfaces; lowering that or lengthening the chain lays a veil over the whole picture. Tone mapping is one ACES fit after `Exposure`, in `HDR_Mapper.frag`.
- Weather: read `WEATHER.md` before changing it. `WeatherField` (`World/WeatherField.cs`, headless) is a pure function of place, time and the world's climate: every machine works out the same sky from the seed and the server's clock with nothing sent, and how wet a place is comes from looking back along the same function, so nothing is stored or stepped. It has its own `WorldRandom` fork. Biomes are what say how wet and warm a place is in absolute terms (`world.Temperature` and `world.Moisture` are ranks within a world). `WeatherSingleton` is settings and live state, `WeatherSystem` keeps its map and running totals by the wind's rules, `WeatherRenderer` is the GPU side (`WeatherData` UBO at binding 9, layout must match `UploadWeatherData`), and `Weather` in `Physics/Weather/` is the CPU API. Everything reads weather from the one map or from `Weather.Here`: don't sample the field per frame. Cloud is applied as light is read, as night is, and a directional light with cascades is taken to be the sun, so lightning has none. The sky is one paraboloid map (`Weather/Sky_Map.frag`, after Patry's "Real-Time Samurai Cinema") that everything reads through `Weather/Sky.glsl`. Rain, snow and ash are `PrecipitationRenderer`, with nothing simulated. Dust is fog: nothing may draw across the whole picture but rain and snow, and no weather may add to `HazeDensity`, as a person found the game hard to see through both (the Clarity section of `WEATHER.md`). Weather's air is the volumetric fog, in `FogLook`s blended by `VolumetricFogSystem.Thicken`, kept to banks, sunk around the hero and pooled in hollows. `NoiseScale` must never change live. Drips come from steps in a view from straight overhead (`Drip_Sources.frag`, `Weather/Drip.glsl`), so nothing places them, and they go on after the rain by the same rule as `ReadDrips`. The rain shadow is drawn by the sun's shadow passes, and geometry reads last frame's, so its matrix only goes live in `FinishRainShadow`. After any change here run `Dino WorldLab weather`.
- Wet surfaces: every material gets wet in the geometry pass (`Weather/Wetness.glsl`), so nothing downstream needs to know. A material's wetness factor is its porosity, a line in `TextureGenerator.SetPorosity`: a new material needs one. Puddles lie where `TerrainSurface.Hollow` says, in the alpha of the terrain's grass map, and `HollowAt` is the same rule for the CPU, which `PuddleLevel` in `GameSounds.cs` has to agree with. A wet surface reflects more than physics says on purpose, as water seen from this camera's 67° is nearly black (`surfaceF0`, `WATER_SHEEN`): smoothness is the only sign of water the G-buffer has, so don't make dry materials that smooth.
- Reflections: read the Reflections section of `WEATHER.md`. `ScreenSpaceReflectionRenderer` is the only place surfaces reflect what's around them: rays through a depth pyramid, drawn from each surface's GGX lobe, shared with neighbours, held by a history that follows the mirror image, and composited per sample. Rays off the ground mostly leave the screen from this camera, so the fallback (the rain shadow for what's overhead, then the sky map) is most of what's seen. Everything `reflectionWanted` turns away reflects the sky in `Ambient_Light.frag` instead, for one lookup, and every pass must ask it of the same stored values. `--render reflectiondebug=N` shows each part, and judge any of this moving.
- Night: `NightfallSingleton.Amount` turns the sun to moonlight and the sky to night, in `SkySYstem`, as light is read: nothing writes to the sun or sky, so read them through `SkySYstem.AtThisHour`, and `VolumetricFogSystem` applies its `FogGlow` the same way (fog with little light to scatter only darkens what's behind it). The moon shines from where the sun is, so shadows hold still as day goes. `AmbienceSystem` raises it near a graveyard, per player, on the client only; `LightingSettings.Night` (F3, `--render night=1`) forces it anywhere. Churchyards (`SiteKind.Graveyard`) always have a church, standing where the land and any road running through allow; a road that ends there is cut back to its door before roads are reserved. `WorldValidator` fails one with no church, or with spawns pushed outside the wall. Anything that stands in the middle of a site can't assume its centre is open ground: `RepairSpawns` silently moves or deletes spawns the `Passable` flood can't reach, so leave rows a character can walk between (`CharacterRadius` is 1.1). `SiteDefinition.Label` seeds that kind's random fork: renaming one moves every site of it in every world. `WorldLab plan --nth N` draws the Nth site of a kind.
- Sound is made, never stored: read `SOUND.md` before changing it. `Dino Engine/Sound/` is headless and talks to WASAPI by COM interop, so it adds no library. `Audio` is the game's whole view of it, and does nothing until `Audio.Start`, so a server needn't ask. A `SoundDefinition` is a recipe run on worker threads into a `SoundPool` of takes that are replaced as they're heard; a `LiveDefinition` is a `LiveSound` made while it plays. Recipes are in `Sound/Content/`, one catalogue class per family, marked `[SoundCollection]`, and the toolkit they use is in `Sound/Synthesis/`. New sounds need no registering. The audio thread never allocates, locks or waits, and `check` proves it. Draw only from `take.Random`. Level a sound with `Mastering.Target` and stand it out with `Presence`, not by raising its gain. Sound quality was tuned against spectra and envelope statistics of real recordings, not by ear, so a person's opinion outranks those numbers. After any change here run `dotnet "Dino SoundLab/bin/Release/net8.0/Dino SoundLab.dll" check`, and `device` if `Sound/Output/` changed. `--record file.wav` saves what the mixer sends out on a scripted run, which keeps quiet unless given `--sound true`. F3 has a Sound window for hearing everything, music moods and intensity included. The client side is `Dino Defenders/Client/GameSounds.cs`: anything that can be read from what's drawn is, in `CharacterSoundSystem`, and what can't comes as a `SoundEvent`. Wind and water follow what's on screen (`WindSample.Crest`, `WaterSingleton.ShorePhase`), and `GroundUnder` says what a foot lands on: read the SOUND.md section on how the game uses it before changing any of them. A person heard this and called the wind too loud and noisy and the footsteps poor, so `check` now fails hiss in the wind and grounds that sound alike.
- Music is composed live: read the Music section of `SOUND.md` before changing it. `Dino Engine/Sound/Music/` is headless. `Music` is the game's whole view of it (`Begin`, `Mood`, `Intensity`, `Play`, `End`); `MusicDirectorSystem` in `Dino Defenders/Client/MusicDirector.cs` drives it, on the client only. A kind of music is an entry in `Styles`, a table of `Part`s. `Level` is how hard a part plays and changes its timbre; `Fader` is where it sits in the mix, so balance with that. `MeasuredSpectra.cs` is generated from SHARC, so don't tune it by hand. Each `Composer` bar is written just before it's due, on the orchestra's own thread, and a fault there leaves a gap in the music and touches nothing else. How one style hands over to another is `Bridge`, and `MoodHold` keeps the Director from following every flicker: keep what was playing going through a handover, and long notes in a bridge on its pivot chord. After any change here run `dotnet "Dino SoundLab/bin/Release/net8.0/Dino SoundLab.dll" musiccheck --count 60`: faults that only show in one world in twenty are real. It proves music isn't wrong, not that it's good. `--music v` sets its level on a scripted run, and 0 leaves the rest of the mix to be measured.
- GUI lives in `Dino Engine/GUI/` (retained-mode element tree, not ECS). `Engine.Gui` is the `GuiContext`; it updates before game/world update and renders to the back buffer at the end of `RenderEngine.Render`. Gameplay input must check `Engine.Gui.WantsMouse` / `WantsKeyboard`. A hidden element isn't updated, so one that sets its own `Visible` in `Updated` can never come back: set it from a parent that stays visible. Text uses a built-in TrueType parser/rasterizer reading OS fonts (`GUI/Text/`), no font assets. Shaders: `Shaders/GUI.vert/.frag` (uniform lines must be `uniform type name;` at column 0 for `ShaderProgram`'s parser). Debug overlay (F3): `GUI/Debug/`.
